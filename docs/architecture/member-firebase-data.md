# Member Firebase data ownership

The existing Firebase deployment uses organization-scoped collections. Chapter 4 describes logical entities, including top-level `users` and `workoutSessions`; its example paths are not a migration command. Keep the deployed paths and rules as the physical contract until each feature has a tested migration. Chapter 3's member profile requirement and the sequence diagram's post-setup Home transition are implemented against these paths.

| Data | Canonical path | Owner and purpose |
| --- | --- | --- |
| Identity and display name | `users/{uid}` | Provisioning service; the mobile client reads its own account. |
| Role, status, branches | `orgs/{orgId}/members/{uid}` | Provisioning/staff; client must never derive authorization from fitness answers. |
| Fitness answers | `orgs/{orgId}/profiles/{uid}` | Member; one bounded, schema-versioned document with measurements and goal categories. |
| Notification and voice choices | `orgs/{orgId}/preferences/{uid}` | Member; one bounded, schema-versioned document. Missing means all choices are off. Delivery services must consult these choices, and device push permission remains separate. |
| Workout session | `orgs/{orgId}/workoutSessions/{sessionId}` | Workout acceptance service; immutable accepted facts, scoped by `memberId`. |
| Published routine read model | `orgs/{orgId}/content/{contentId}` | Admin-published organization content. `kind: routine`, `status: published`, `schemaVersion: 1`, `sourceBlueprintId`, `title`, `estimatedMinutes`, and a bounded `exercises` array. Each exercise carries a stable `exerciseId` plus display name, sets and reps. It is a catalog item, not an assignment or workout record. |
| Exercise catalog | `orgs/{orgId}/exerciseVideos/{exerciseId}` | Admin/Staff create, list, and update. Schema v1: `exerciseName`, `muscleCategory`, `videoUrl`, `isActive`; document ID is the stable exercise ID. Hard deletion is denied. |
| Routine blueprint | `orgs/{orgId}/routineBlueprints/{templateId}` | Admin/Staff create, list, and update. Schema v1 includes `name`, `sessionDurationMin`, and `days`; each day has `dayNumber` and `exercises`, and each exercise reference has only `exerciseId`, `sets`, and `reps`. Existing builder metadata such as level, goal, tags, equipment and image URL remains optional. Hard deletion is denied. |
| Booking and payment | `orgs/{orgId}/bookings/{bookingId}` and future commerce collections | Server commands and webhook reconciliation. |
| Rewards | Future reward account and append-only ledger | Server awards; a client cannot write its own points or streak. |

Home, reports, and Multifaceted recommendations should read purpose-built projections derived from those source records. A future `orgs/{orgId}/memberSummaries/{uid}` can hold bounded fields such as weekly session count, last accepted workout, next confirmed booking ID, reward balance, and `computedAt`. It must not become a second writable profile or contain unlimited session arrays. Server handlers should update projections idempotently after accepting source events, using event IDs and a versioned projection schema. The client should show “unavailable” when a projection is absent or stale, rather than interpreting it as zero activity.

For cross-member Multifaceted analysis, keep private source records organization-scoped and build aggregate documents server-side with branch/time/exercise dimensions and minimum cohort/privacy rules. Do not query every member profile from a mobile client. Aggregate definitions should record the source event range and algorithm version so analytics can be recomputed after scoring changes. Add indexes for the exact authorized query shapes when a feature is implemented; no broad collection-group access is implied.

The current mobile slice reads a verified member's profile, preferences, account display name, and the first published routine catalog item for the member's organization. Home and Workout reuse the mock layouts and show that published routine when present. The routine detail lists its real exercise names and targets; tutorial playback and session recording remain unavailable. Other mock-only controls respond with an unavailable message rather than opening demo data. Profile and Settings save real data. Reward, booking, membership, coach, and report records remain disconnected until their source data and authorization paths are implemented. The mock build remains a separate prototype data source.

Publishing this read model requires the `publishRoutineCommand` callable: it derives authorization from the authenticated UID's organization membership, loads the blueprint and active exercise catalog records server-side, and composes at most 50 exercise rows. Each published row contains `exerciseId`, `name`, `category`, `muscleGroup`, `sets`, `reps`, and `dayNumber`. The client command accepts only `schemaVersion`, `requestId`, `organizationId`, and `blueprintId`; it cannot submit publication status or read-model fields. Mobile clients cannot write `content`. The `content(status, kind)` Firestore index was deployed to the development project `gainpath-0619` on 2026-10-01. A published routine remains a catalog item and never becomes a per-member workout history or assignment.
