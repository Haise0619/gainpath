## Authority and visibility

- Firebase Auth UID and verified-email token authenticate the caller. Current server `users/{uid}` assignment and organization membership determine organization/role/status/branches; client-selected role is never authority. Reuse [auth-context.ts](../../functions/src/platform/auth-context.ts), adding command-local organization consistency and canonical role checks.
- [FirebaseAuthRepository](../../packages/gainpath_data/lib/src/firebase_auth_repository.dart) maps `staff` and `branch_staff` to `AppRole.admin`. Backend accepts canonical `admin/staff/coach/member`. **B1 publication is canonical Admin-only**; staff aliases do not gain publication authority. Admin composition reads its own raw membership for capability display; the command independently rejects staff. No global role-model rewrite is needed.
- Coach authoring is own UID only, never name/email-based matching. A Coach cannot change branch assignment, account identity, publication state or verification. Admin publication copies current server-assigned active branch IDs; branch IDs must be unique valid document IDs, at most 8 for this bounded command, and every referenced branch must be active. Nonempty invalid/inactive assignments block publication rather than silently changing membership.
- Directory visibility remains **organization-wide**, matching current Rules. A Member may see a Coach assigned to another branch in their organization; future booking must independently require matching branch access. This is directory browsing, not availability or booking eligibility.
- Private contact/auth data remains in existing identity records. Certification uploads/review are excluded. Publication is approval of the public listing, **not certification verification**; there is no `verified` badge/field added by B1.

## Smallest safe storage choice

Direct Coach editing of the existing published document would expose unreviewed changes. Putting draft/private fields alongside public fields in that same Firestore document would expose the entire document to authorized Members: client presentation cannot enforce field privacy. A callable-only directory would discard the existing scoped reader/Rules foundation.

**Recommended:** one new private draft collection, `orgs/{org}/coachProfiles/{uid}`, and reuse `orgs/{org}/coaches/{uid}` as the public projection. Both use stable Auth UID document IDs. Two small trusted commands own all mutations; Rules continue denying direct writes. This is a necessary new profile contract because there is no real authoring schema. There is no booking/workout/history migration and no duplicate account system.

| Field | Private profile v1 | Public projection v1 | Authority / validation |
|---|---|---|---|
| `schemaVersion` | 1 | 1 | Server |
| `revision` | Positive integer | Positive integer | Server increments each successful mutation; absence baseline is 0 only when document is missing |
| `displayName` | Required | Published copy | Coach professional display name, trimmed 1–80 characters; does not update Auth/users/members |
| `specialty` | Required | Published copy | Coach, trimmed 1–80 characters |
| `bio` | Required | Published copy | Coach, trimmed 0–1000 characters; plain text |
| `specializationTags` | Required | Published copy | Coach, 1–8 unique trimmed strings, each 1–40 characters |
| `yearsExperience` | Null or integer | Published copy | Coach self-reported, 0–60; nullable and labeled self-reported when shown |
| `createdAtMillis`, `updatedAtMillis` | Required | Required | Server clock; immutable created time, updated time per successful mutation |
| `status` | Absent | `published` or `inactive` | Admin command only |
| `branchIds` | Absent | Required bounded list | Derived from current Coach membership and active branches, never caller-supplied |
| `sourceRevision` | Absent | Private revision reviewed | Server publication provenance |
| `publishedAtMillis` | Absent | Required after publication | Server; set on publication, preserved on deactivation |

Public profile has **only** the public columns above. It contains no email, phone, certification paths/documents, private notes, Auth/provider metadata, fees, availability, ratings/reviews, response times, completed-session counts or earnings. Use an avatar placeholder; photo/media authoring is deferred. Do not construct the legacy `Coach` entity with invented zero metrics: its required numeric fields are prototype assumptions, not proof of real data. Add small immutable profile/directory types and an async port beside the existing contracts; keep the legacy synchronous [CoachRepository](../../packages/gainpath_domain/lib/src/identity/repositories/coach_repository.dart) and mock seed behavior compatible.

No initial migration is needed in the inspected organization because both live Coach membership/profile sources are absent. Implementations must still fail closed on existing incompatible versions/revisions or unexpected public fields, rather than overwrite/drop them. Unknown fields on a private draft are preserved by patching against the transaction's current document and are never copied to public content. No destructive cleanup is included.

## Trusted operations and concurrency

### `saveCoachProfileCommand`

Input v1: `{schemaVersion:1, organizationId, requestId, expectedRevision, patch}`. Allowed patch keys are exactly `displayName`, `specialty`, `bio`, `specializationTags`, `yearsExperience`. At least one intentional field change; creation requires all five keys (yearsExperience may be null). Reject unknown command/patch keys. Target UID is always the caller; no target coach ID accepted.

Require signed-in verified caller; current matching user assignment and active canonical Coach membership; valid nonempty branch assignments and active organization. In a transaction, read authority, receipt and current draft before writing. Compare immutable expected revision, validate the resulting profile, update only patch fields plus incremented revision/server timestamps, preserve created time and unrelated private fields, and record a receipt. Use existing [DocumentStore](../../functions/src/platform/firestore/store.ts)/[FirestoreStore](../../functions/src/platform/firestore/firestore-store.ts); its `set` can write `{...current, ...validatedPatch, revision, updatedAtMillis}` after checking current state. No new transaction framework is needed.

Save never writes the public projection, membership, Auth, availability or bookings. A previously published profile remains its last Admin-reviewed snapshot; Coach sees that saved edits await publication.

### `setCoachDirectoryStatusCommand`

Input v1: `{schemaVersion:1, organizationId, coachId, requestId, action, expectedPublicRevision, expectedProfileRevision, expectedCoachBranchIds}`. `action` is `publish` or `deactivate`. Require expectedProfileRevision and expectedCoachBranchIds for publish; both must be omitted for deactivate. Target is a valid UID document ID within the requested organization. Admin review loads target membership using existing Admin read permissions and captures the immutable branch-ID baseline; the transaction compares its canonical set with current membership before deriving public branches. The submitted baseline is a concurrency assertion, never authorization or a requested branch reassignment.

Canonical active verified Admin with matching server assignment only. **Publish:** verify the target Auth account exists, is not disabled and has a verified email via an injected server-side identity reader backed by `getAuth().getUser`. This is an observation before the Firestore transaction, not an atomic Auth/Firestore guarantee. Transactionally recheck target user assignment, active Coach membership, active organization/branches, private source revision and current public revision. Project only the allowlisted professional fields with derived branch IDs; increment public revision and update publication timestamps. Reject stale source/public state. Do not allow self-submitted `status`, `verified`, `branchIds` or aggregate fields.

**Deactivate:** require an existing compatible public document and expected public revision; set only `status: inactive`, revision and updated timestamp, retaining ID, professional snapshot, sourceRevision, branchIds and original times. It must work even when the target account is now disabled/suspended or its draft is missing. It does not require a matching current draft or currently eligible target Auth account. It does not suspend identity or cancel bookings. No hard delete.

Both commands use existing commandReceipts/keyOf patterns: key includes command, actor and requestId; fingerprint includes all parsed scope/action/expected revisions/patch fields with canonical ordering. Same requestId/same input replays the receipt **only after current actor authorization is checked**; same requestId/different input rejects. New intent gets a new ID; transport retry keeps the same ID and immutable input. Receipt replay is not the latest document snapshot; the app reads current state after a successful result.

Deactivation of an already inactive compatible record with a matching revision is a receipt-backed no-op: do not change the document revision/timestamps. Fresh publication is an intentional new snapshot and increments public revision even when professional values are unchanged.

Transaction retries never replace expected revisions with newly read values. Conflict returns sanitized `aborted`, preserves the entered form, disables Save/Publish and requires explicit discard/reload. Missing documents, authorization loss and unsupported versions have distinct safe states. No raw Firestore maps or request bodies in logs/errors. Client adapters/controller lifetimes latch invalidation on account/org/role/branch-session drift and discard stale reads/saves; server checks remain the security boundary when client state is old. A request committed before logout cannot be undone by client cancellation and must not show success in a different account.

**Lifecycle limit:** current Rules do not join every published Coach row to current target membership/Auth state. Admin directory deactivation hides it; future account suspension/reassignment workflows must atomically deactivate that projection, while booking already rechecks live membership. B1 cannot claim automatic Auth-disable-to-directory withdrawal. Do not add a per-row Auth/Firestore join or a broad lifecycle trigger during this slice. Document and test this limit; live publication requires a provisioned active Coach, and any later account mutation needs its own integrity workflow.

## Rules, indexes and callable configuration

New `coachProfiles` Rules: owner `get` only for verified active canonical Coach; canonical Admin get/list within the organization; all client create/update/delete denied. Ordinary Members, other Coaches and staff cannot read drafts. Owner missing-document get must be allowed so creation has an honest empty state. Add a narrow B1 helper requiring existing active verified membership **and** `users/{callerUid}.organizationId == orgId` **and** membership `organizationId == orgId`; stale active membership in a former organization must not permit reads. Use this helper for both private profiles and public `coaches`, without changing unrelated collections. For unpublished public documents, owner access additionally requires current canonical Coach role; ordinary Members read only published documents, even if a former Coach UID happens to equal a public document ID. Canonical Admin retains scoped unpublished access. All public client writes remain denied. These limited public Rules changes are necessary for the B1 reassignment/Member visibility contract; they do not add write permissions. No Storage Rules are needed.

Member read: organization `coaches`, `status == published`, document-ID order, page size 20 plus one lookahead, cursor last returned ID, server refresh. Exact detail revalidation uses an authorized bounded status/doc-ID range and exact-ID match, reusing A1's proven query approach. Withdrawn rows must not reopen from cached cards; failures are unavailable/error, not empty success. Admin exposes two bounded lists using document-ID paging: private drafts and public projections (including inactive). Deduplicate any combined display by UID. This second entry point makes a public profile withdrawable even if its private draft was deleted outside B1. Publication review reads matching private/public documents plus current target membership; missing draft disables Publish but retains Deactivate. No new composite index is expected for these simple query shapes; confirm exact emulator/query behavior, then retain live index verification as an activation gate if an index is required. Do not deploy speculative indexes.

Add exactly two callable exports to [index.ts](../../functions/src/index.ts), following the existing authenticated publisher wrapper/error mapping. Existing clients contain no App Check initialization; B1 proposes the existing publisher's callable configuration with mandatory email/current-membership checks. Do not disable existing App Check enforcement on booking/workout handlers. App Check rollout is a separately reviewed activation/hardening decision, not silently claimed operational by B1. Test callable authorization/error mapping; a service smoke alone is not callable-network evidence.
