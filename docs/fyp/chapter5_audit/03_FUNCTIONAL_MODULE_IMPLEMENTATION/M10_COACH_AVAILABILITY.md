# M10 — Coach availability and roster

**Status:** Implemented but Not Fully Verified. Source handles recurring schedules, special dates and existing reservations. Actual roster settings/time zone/cap are runtime organization data and were not inspected live.

**Interaction:** Coach selects Calendar / Availability, sees weekly hours and date coverage, and edits standard windows, specific-date hours or exceptions through scoped editor sheets. Read UI distinguishes no configured availability, selected date unavailable, and backend error. Classes include `CoachAvailabilityCubit`, `AvailabilityPage`, `CoachRosterEditor`, `WeeklyHoursSheet`, `CoachSpecificDateSheet`, and `CoachTimeExceptionSheet`. Source in `apps/mobile/lib/features/coaching/application/coach_availability_cubit.dart`, `apps/mobile/lib/features/coaching/presentation/coach/`, `apps/mobile/lib/infrastructure/firebase/firebase_coach_availability_repository.dart`.

**Data and workflow:** Roster at `orgs/{org}/coachAvailability/{uid}` plus dated override data. Revision, scoped eligible branch IDs, recurring windows, local date and timezone are parsed with `orgs/{org}/settings/booking` and current active assignments. `dateGrid` derives UTC slot instants for a local date using the organization timezone, in half-hour increments, then validates local boundary alignment and permitted branch. Saved per-day windows are validated against policy, future scope, existing overlapping locks and branch authority. The roster save transaction reads affected locks, including absent ones, and pinned prior coverage can preserve an existing reservation while changing recurring hours. Dated overrides take precedence. Booking hold, reschedule and group class publication consume the same effective coverage and coach/time locks; currently assigned branch visibility is a separate scope check. See `functions/src/modules/coaching/coach-availability-contracts.ts:5,39–85`, `coach-availability-service.ts:39–end`, `coach-roster-service.ts:61–end`. Organization policy accepts a daily active booking count per Member in the range 1–32 and hold duration 1–30 minutes; these are valid configuration bounds, not verified production settings.
