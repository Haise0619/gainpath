# Source-derived storage model

Paths are relative to Firestore unless marked Storage or device. `O` below denotes `orgs/{organizationId}`. IDs in these examples are symbolic. Numeric fields ending in `Millis` are epoch milliseconds unless the validator specifies otherwise. Some direct authoring records instead use Firestore Timestamp. The [declared composite indexes](firestore_indexes.csv) are a separate configuration snapshot. Live schema coverage and deployed indexes were unable to be verified.

| Record and path | Important fields/type, relationship and lifecycle | Authority and source |
|---|---|---|
| `users/{uid}`; `O/members/{uid}`; `O/branches/{branchId}` | ID matches Firebase Auth; organization/primary branch strings, role and active/pending state, branch ID array, email and display name, schema version and recorded millis. Member and branch are denormalized into identity scope. | Registration writes canonical data transactionally. Lifecycle writes can require recent verified auth and revision. `member-provisioning.ts:36–117`; `firebase/firestore.rules:240–342`. |
| `O/profiles/{uid}`; `goals/{goalId}/revisions/{revision}`; `O/preferences/{uid}` | Member physical/fitness context, activity and experience, fitness goal values and revision history, and mutable notification/personal settings. | Owner and scoped administrative access governed per field. `firebase/firestore.rules:343–447`; fitness profile and preferences repositories. |
| `O/memberLifecycleCommands/{uid}/…` | Idempotent request/revision receipt and account revocation lifecycle. Auth refresh-token revocation is an external side effect. | Callable server-owned writes. `member-account-lifecycle.ts:96–216`; Rules deny direct access. |
| `O/membershipAccounts/{uid}`; membership billing state, upgrade quotes, checkout recovery | Account holds member-specific current term and pending transaction reference. Quote/recovery documents bind a membership operation, expiry and identity. Membership plans include Free, Basic and Premium. | `membership-payment-service.ts:27–31,162–255,264–352`; membership entitlement service. Commands derive tier from canonical account state. |
| `O/transactions/{id}`; payment `adminCommands` and `adminResults` | Member, plan or booking association, provider/environment, integer MYR minor units, bill ID, fulfillment and payment status, refund/audit metadata. Admin command fingerprints recognize exact retries. | Backend settlement and review. `booking-payment-admin.ts:80–132`; `membership-payment-service.ts`. |
| `O/bookings/{bookingId}`, consultation/current, review/current, externalDelivery and messages | Member/Coach/branch references, localDate, interval millis and status. Lifecycle handles hold, confirmation, completion, cancellation, expiration and refund states. Notes, one-review records, communications and provider receipts are separately scoped. Some messages are pair-scoped rather than booking-scoped. | `booking-service.ts:34–84`; `booking-consultation-service.ts`; `booking-review-service.ts`; `pair-conversation-service.ts`; Rules :763–789. |
| `O/coachAvailability/{coachId}/days/{date}` and parent | Weekly roster, daily overrides, time windows and branch/capacity links. School/holiday-style free-time blocks should be described using actual roster windows and exceptions. | Coach/authorized Admin read/manage via callable and server scheduling transactions. `booking-validation.ts:82–103`; `coach-availability-service.ts:63–133`. |
| `O/coachProfiles/{coachId}`; `O/coaches/{coachId}` | Private profile and certifications/history versus published denormalized directory projection. Status and branch tags regulate visibility. | Rules :750–760 and :835–856. Coach profile and management callables update via controlled commands. |
| `O/exerciseVideos/{exerciseId}`; `O/content/{contentId}`; `routineBlueprints{,V2}`; `O/gymEquipment/{equipmentId}` | Exercise IDs, status, mode, defaults and revision metadata; routine blueprint/published projection; equipment activation and metadata. Program references are versioned and scoped. | Publication and content authoring Functions plus Rules. `firebase/firestore.rules:448–493,659–692`. |
| `O/workoutConsents/{uid}`; `O/workoutSessions/{sessionId}` | Owner-scoped consent and accepted measured session contract. Current accepted workout tuple allowlist is empty. | Backend owns writes, client cannot manufacture acceptance. `workout-service.ts`; Rules :790–799. |
| `O/members/{uid}/workoutBackups/{kind-id}/revisions/{digest}` and parent | String kind, ID, digest and payloadJson, schemaVersion, provisional classification, numeric updatedAtMillis. Per-record revisions, exact repeats return backed_up, conflicting data stays visible. | `workout-backup.ts:43–76`. Separate from admitted/accepted sessions and permissions for Module 13. |
| `O/appCheckInProfiles/{uid}/claims`; `O/rewardBalances/{uid}`; `O/rewardEvents`, `rewardAwards`, `rewardRedemptions`, `rewardItems`, `rewardPolicies/current` | Claim day, source ID and points; balance and recent redemption links; deterministic award IDs, cap keys, priced items, immutable event evidence and voucher/fulfillment state. | Server derives award and mutation eligibility. `verified-rewards-service.ts:125–201`; `verified-rewards-callables.ts:38–60`. |
| `O/chatbotDisclaimer/config`; `O/members/{uid}/chatbot/state` | Versioned disclaimer and isolated conversation/consent/usage state. Prompt assembly reads only scoped, bounded progress and selected published data. | `chatbot-callable.ts:33–43,94–107,183`; Rules :533–578 for authoring. |
| `O/recommendationLeads/{leadId}`; `O/notifications/{id}`; `datasetAssignments/{uid}` and FYP cohort | Lead input/source fingerprint, state/revision and destination; recipient-specific notices and durable delivery state. Revocable cohort assignment scopes synthetic inputs separately. | `recommendation-queue-generation.ts:119–138`, `recommendation-delivery.ts:134–144`; Rules :801–804 and :862–1013. |
| `O/announcements/{id}` and `O/legalDocuments/{kind}`; Member legalConsents and version receipts | Announcement title/body, revision, validity and state. Legal documents have draft/published revisions and Member per-version acceptance. Legacy `complianceDocuments/config` also has its own authoring Rules. | `firebase/firestore.rules:495–530,614–657` and `compliance-service.ts:22–24,38–94`. Branch-scoped announcement source/Rules mismatch tracked separately. |
| Storage `orgs/{orgId}/...` | Owner/member media, coach/private certification paths and author-owned equipment/exercise/reward media. Storage objects carry MIME and size constraints. Firestore documents store scoped metadata or asset references. | `firebase/storage.rules:24–203`; direct public access is not inferred from a URL-shaped field. |
| Device files | Scoped workout session list/outbox, parsed and validated JSON, local routine checkpoints, program enrollment, backup and game history metadata. | `apps/mobile/lib/infrastructure/local/` and module-specific stores. Device file persistence is separate from Firestore lifecycle. |

Chapter 4 §4.2.2 lists mostly top-level operational collections and a separate `coach_public_profiles` projection. The source places most operation paths below an organization, with shared `users` and separately authorized `datasetAssignments`. Booking/reward/backup subcollections and dual local/cloud data lifecycles require a revised data dictionary. Use the typed timestamp contract from the actual adapter per collection.
